# M1 多数据库架构升级规划

> 版本：v0.1 | 日期：2026-11-20 | 状态：规划中
> 需求对应：[需求文档](需求文档.md) | 功能清单：[功能模块清单](功能模块清单.md) | 架构设计：[架构设计](架构设计.md)

本文档是多数据库架构升级的实施底稿，用于在长周期改造中记录边界、切片和进度，避免遗漏。**细节以代码和 XML 注释为单一事实源，本文只记录决策、边界和阶段目标。**

## 1. 目标与非目标

### 1.1 目标

- 在不影响核心关系型数据库（SqlServer/MySql/PostgreSQL/Oracle/SQLite）基础 CRUD、批量、迁移、分页的前提下，建立可扩展的多数据库能力模型。
- 用**能力标志**表达“当前连接支持哪些操作”，替代运行时的 `NotSupportedException`、静默 `0/null/false` 和空 `DataTable`。
- 用**方言接口**隔离格式化、参数、分页、类型映射和窗口函数渲染，降低 `IDatabase` 的职责密度。
- 让非 SQL 提供者（MongoDB/InfluxDB 等）以“原始命令 + 批量写入”或“明确不支持”的方式接入，而不是伪装成完整 ORM。
- 为窗口函数等大数据分析能力提供方言渲染与能力降级机制。

### 1.2 非目标

- **不一次性把 `IDatabase`/`IDbSession`/`IMetaData` 拆成十几个接口。**
- **不新增 NoSQL 原生查询 API**（需求文档 N3 仍有效）；MongoDB 等只做 Provider 接入、原始命令或能力声明。
- 不改变 DAL 以上公共 API 的语义；DAL 以下允许破坏性调整，但核心关系型路径必须保持行为不变。
- 不为所有数据库承诺完整实体 ORM；非 SQL 数据库可以只支持 DAL 层原始操作。

## 2. 兼容性边界

**DAL 是实体层与数据层的边界。**

| 范围 | 策略 |
|------|------|
| `DAL` 及以上 | 保持公共 API 与行为稳定；必要时只做增量扩展 |
| `DAL` 以下（`IDatabase`/`IDbSession`/`IMetaData`/基类/Provider） | 允许破坏性调整；实体层有直接使用时同步修改 |
| XCode 之外直接使用 DAL 以下接口 | 接受破坏性变更；升级说明中标注 |
| 核心关系型数据库 | 每个切片完成后必须跑通既有 CRUD/批量/迁移/分页测试 |

> 当前已确认：`DbBase`/`DbSession`/`DbMetaData` 已改为 public，并补齐 XML 注释（CS1591 清零）。这是后续外部 Provider 复用基类的前提。

## 3. 拆分边界（核心决策）

### 3.1 保留三个门面

`IDatabase`、`IDbSession`、`IMetaData` **继续作为调用方入口**，不拆成十几个小接口。理由：

- 调用方目前依赖门面完成常见操作，拆散会增加组合复杂度。
- 三个门面的成员虽然多，但 `IDbSession`/`IMetaData` 的大部分成员围绕“执行/元数据”内聚。
- NewLife 原则偏保守：先解决“能力不可见”和“方言混杂”，再考虑门面拆分。

### 3.2 只抽四个可选接口

按引入顺序，逐步抽出：

| 顺序 | 接口 | 职责 | 引入阶段 |
|:----:|------|------|:--------:|
| 1 | `IDbCapabilities` | `DatabaseProfile`、`DatabaseCapability`、`Supports`、`EnsureSupported` | P0 |
| 2 | `IDbDialect` | 名称/值/参数格式化、分页、类型映射、窗口函数渲染 | P0 |
| 3 | `ISchemaReader` | 架构读取（表/字段/索引/视图） | P1 |
| 4 | `ISchemaMigrator` | DDL 生成与执行、迁移 | P2 |
| 5 | `IDatabaseMaintenance` | 备份/恢复/收缩（最后，按需） | P2 |

`DbBase`/`DbSession`/`DbMetaData` 实现这些可选接口；调用方通过扩展方法或类型判断使用。**门面继续转发现有成员，保证旧调用方不受影响。**

### 3.3 不抽的部分

| 成员组 | 保留位置 | 理由 |
|--------|----------|------|
| 连接作用域（`Process`/`ProcessAsync`/`SetShowSql`） | `IDbSession` | 与执行生命周期强相关 |
| 事务（`BeginTransaction`/`Commit`/`Rollback`） | `IDbSession` | 会话级状态，拆出后调用方需要组合 |
| 查询/执行（`Query`/`Execute`/`ExecuteScalar`） | `IDbSession` | 执行面的自然组合 |
| 批量 DML（`Insert`/`Update`/`Upsert`/`Replace`/`InsertIgnore`） | `IDbSession` | `DatabaseCapability.Bulk*` 已能表达；先修一致性，不新增接口 |
| 元数据读取/DDL 门面 | `IMetaData` | 先加 `ISchemaReader`/`ISchemaMigrator` 作为实现接口，门面保留 |

### 3.4 拆分判断规则

只有同时满足以下条件才拆：

1. 有**独立变更原因**（不是同一类逻辑的机械切分）。
2. 有**不同的提供者子集**（有的数据库支持、有的不支持）。
3. 调用方需要**独立判断/替换**（例如能力查询、方言替换）。
4. 拆出后**成员数明显下降**，且不增加调用方的组合负担。

反例：一个方法一个接口、为了“看起来整洁”而拆、把连接/事务/查询拆成调用方必须同时持有的多个接口。

## 4. 目标架构

```
实体层 / Entity / IEntityPersistence
        │  （能力门禁：SQL / EntityCrud）
        ▼
DAL（边界，公共 API 稳定）
        │
        ├── IDatabase（身份/配置/生命周期/门面）
        │       ├── IDbCapabilities（Profile + Capabilities）
        │       └── IDbDialect（格式化/参数/分页/窗口函数）
        │
        ├── IDbSession（连接/事务/查询/执行/批量/门面）
        │       └── ISchemaReader（可选）
        │
        └── IMetaData（元数据门面）
                ├── ISchemaReader
                ├── ISchemaMigrator
                └── IDatabaseMaintenance
```

### 4.1 能力定义

> 能力 = 引擎能力 ∩ 当前连接配置 ∩ XCode 已实现范围。

它描述“XCode 在当前连接上可以安全生成并执行的操作”，不是数据库理论上的全部功能。条件能力（Presto 连接器写、ClickHouse mutation、MongoDB 副本集事务）**默认关闭**，显式开启后再把标志加回来。原生 `Execute` 仍是逃生通道。

### 4.2 `DatabaseCapability` 分组（Int64）

`Int64` 足够；按区间预留，避免后续重编号：

| 位区间 | 用途 | 示例 |
|--------|------|------|
| 0-15 | 核心 DML/DDL/事务 | `Sql`、`Transactions`、`Ddl`、`DatabaseDdl`、`Identity`、`Insert`、`Update`、`Delete`、`Truncate`、`SchemaDiscovery` |
| 16-31 | 查询能力 | `Joins`、`Subqueries`、`GroupBy`、`Having`、`WindowFunctions`、`WindowFrame`、`Cte`、`Union`、`OffsetPaging`、`LimitPaging` |
| 32-47 | 批量/架构/维护 | `BulkInsert`、`BulkUpdate`、`BulkUpsert`、`BulkReplace`、`BulkInsertIgnore`、`SchemaDiscovery`、`TableDescription`、`ColumnDescription`、`Backup`、`Restore`、`Compact` |
| 48-63 | 预留/实验 | `Json`、`Array`、`FullText`、`Geo`、`Graph` 等 |

### 4.3 `DatabaseProfile`

除 flags 外，还需要非布尔特征：

- `DatabaseModel`：Relational / Document / TimeSeries / Columnar / Federated / KeyValue / Graph
- `QueryLanguage`：Sql / Flux / InfluxQl / MongoCommand / Native
- `MaxMigration`：Off / ReadOnly / On / Full；有效迁移 = `Min(用户 Migration, MaxMigration)`
- `LongTextLength`、`ParameterPrefix`、`MaxIdentifierLength`、`MaxParameters`
- `DefaultNameFormat`、`PagingStyle`、`IdentityStrategy`

### 4.4 兼容与迁移

- `IDbCapabilities`/`IDbDialect` 先作为**可选接口**，由 `DbBase` 实现。
- 调用方用扩展方法 `GetCapabilities()`/`GetDialect()`；`IDatabase` 成员暂不变。
- `BatchCapability` 已合并到 `DatabaseCapability.Bulk*`；`DAL.BatchCapabilities` 仅保留过渡别名，内部统一使用 `Capabilities`。
- 下一个大版本再评估是否把 `Capabilities`/`Dialect` 提升为 `IDatabase` 正式成员。

## 5. 窗口函数架构

### 5.1 现状

- `SelectBuilder.Window` 是字符串；`WindowFunction` 只是字符串拼接助手。
- 没有能力判断；不支持窗口函数的数据库会在执行时报 SQL 语法错误。
- 没有统一的帧（ROWS/RANGE BETWEEN）和方言差异处理。

### 5.2 目标

- `WindowExpression` AST：
  - `WindowFunctionKind`：`RowNumber`/`Rank`/`DenseRank`/`Ntile`/`Lag`/`Lead`/`FirstValue`/`LastValue`/`Aggregate`
  - `WindowSpec`：`PartitionBy`、`OrderBy`、`WindowFrame`
  - `WindowFrame`：`Rows`/`Range`、`UnboundedPreceding`/`CurrentRow`/`UnboundedFollowing`/`Offset`
  - `Alias`
- `IDbDialect`：
  - `Boolean SupportsWindowFunctions`
  - `String RenderWindow(WindowExpression expression)`
  - `String RenderWindowFrame(WindowFrame frame)`
- `SelectBuilder` 保留 `Window` 字符串兼容；新增 `WindowExpression` 属性，由 DAL 在生成最终 SQL 时按方言渲染。
- 能力不足时：
  - 默认抛出带操作名的 `NotSupportedException`；
  - 仅对小结果集提供显式 `WindowFallback.InMemory`（默认关闭），避免大数据场景静默降级。

### 5.3 方言差异

| 方言 | 关注点 |
|------|--------|
| SqlServer | `OVER`、`ROWS/RANGE`、`TOP` 与窗口函数组合 |
| PostgreSQL | 标准 `OVER`、`FILTER`、命名窗口 |
| MySql 8+ | 标准 `OVER`；5.7 不支持 |
| SQLite 3.25+ | 标准 `OVER`；旧版本不支持 |
| Oracle | 标准 `OVER`；`ROWNUM` 与窗口函数组合 |
| DuckDB | 标准 `OVER` |
| ClickHouse | 窗口函数支持有限，按版本声明 |
| Presto/Trino | 标准 `OVER` |
| InfluxDB/MongoDB | 不支持，能力标志关闭 |

## 6. 非 SQL 数据库与 `IEntityPersistence`

### 6.1 问题

`IEntityPersistence` 直接拼 `Insert Into/Update/Delete`，`SelectBuilder`/`InsertBuilder` 也是 SQL 专用。当前 MongoDB/InfluxDB 的实体写入会落到 SQL 路径，导致“注册了但不可用”。

### 6.2 方案

1. **P0 能力门禁**：`EntityPersistence`/`EntitySession` 在拼 SQL 前检查 `DatabaseCapability.Sql`/`EntityCrud`；非 SQL 提供者明确抛出“该数据库不支持实体 ORM，请使用 DAL 原始命令”。
2. **P1 Provider 持久化工厂**：利用 `IEntityFactory.Persistence` 可写的现有扩展点，新增 `IEntityPersistenceFactory`（或 `IEntityPersistenceProvider`）：
   - `IEntityPersistence Create(IEntityFactory factory, IDatabase db)`；
   - 默认返回 `EntityPersistence`；
   - 非 SQL 提供者可返回原生适配器，或返回“不支持”的实现。
3. **P2 原生适配器**：仅在有真实需求时为 MongoDB/InfluxDB 实现 `IEntityPersistence`；否则保持原始命令模式。
4. **不新增 NoSQL 原生查询 DSL**（N3）。

## 8. 测试策略

| 层级 | 内容 | 时机 |
|------|------|------|
| L1 | 受影响纯单元测试（能力矩阵、方言渲染、SQL 快照） | 每个切片 |
| L2 | SQLite 集成测试（CRUD/批量/迁移/窗口函数） | 每批切片 |
| L3 | 关系型真库冒烟（SqlServer/MySql/PostgreSQL/Oracle，按环境可用） | 里程碑 |
| L4 | 非 SQL 真库冒烟（Mongo/Influx/ClickHouse/TDengine） | 按环境，可跳过 |

**能力一致性测试**（S2 必做）：

- 每个注册 Provider 都有 `Profile` 和 `Capabilities`。
- `Bulk*` 标志与 Session 批量方法实现一致（标志为真必须有实现）。
- 标志为真时，对应 Session 方法必须重写或基类有通用实现。
- `MaxMigration=Off` 的 Provider 不得执行 DDL。
- 无 `SchemaDiscovery` 的 Provider 不得返回 `null` 让调用方误判。

## 11. 已确认与待确认决策

**已确认：**

- `BatchCapability` 直接合并到 `DatabaseCapability`，接受破坏性变更；`DAL.BatchCapabilities` 仅保留过渡别名。
- 窗口函数不支持时默认抛异常；内存回退必须显式开启。
- 拆分顺序：先做能力模型（S2），再做 `IDbDialect`（S3）。

**待确认：**

1. `IDbDialect` 是否在下一个大版本提升为 `IDatabase.Dialect` 正式成员？（当前建议：先可选接口）
2. `ISchemaMigrator` 的类型化 DDL API 采用“每个操作一个方法”还是“类型化命令对象”？（当前建议：命令对象 + 少量便捷方法）
3. MongoDB/InfluxDB 是否投入原生 `IEntityPersistence` 适配器？（当前建议：先原始命令模式，按真实需求再投入）
