# XCode 插件化架构

XCode 的主脉络是**实体添删改查**：`Entity<T>` → `EntitySession` → `IEntityPersistence` → `IDbSession` → `IDatabase`。缓存、分片和批量写入是这条主脉络上的核心能力，不能为了“插件化”把它们抽空。

插件化的目标不是把所有类都变成插件，而是把**可替换的实现**和**可选的横切机制**放到边界上，让核心 CRUD 链路保持稳定、可读、可测试。

---

## 1. 两层过滤器

| 层 | 接口 | 位置 | 适合处理 |
|----|------|------|----------|
| 实体操作层 | `IEntityFilter` | `Entity<T>.DoAction`、`EntitySession` 查询、缓存读取 | 租户隔离、行级数据权限、审计、字段填充、业务校验 |
| 数据库命令层 | `IDbCommandFilter` | `DbSession.Execute/ExecuteAsync` | SQL 改写、慢 SQL、命令审计、参数脱敏、命令级限流 |

两层职责不要混用：

- 需要知道实体、`EntityContext`、`Entities` 或缓存结果的，用 `IEntityFilter`。
- 只需要看 SQL/`DbCommand`、连原始 SQL 和 DAL 直连也要覆盖的，用 `IDbCommandFilter`。

`IDbCommandFilter` 能覆盖原始 SQL，但不能替代实体层的租户/数据权限；实体过滤器能理解字段和实体归属，但不应直接拼数据库命令。

### 1.1 IDbCommandFilter 示例

```csharp
public sealed class SqlAuditFilter : DbCommandFilter
{
    public override void OnExecuting(DbCommandContext context)
    {
        context.Items["start"] = Runtime.TickCount64;
    }

    public override void OnExecuted(DbCommandContext context)
    {
        var start = context.Items["start"].ToLong();
        var cost = Runtime.TickCount64 - start;
        if (cost > 500)
            XTrace.WriteLine("Slow SQL {0}ms: {1}", cost, context.Sql);
    }
}

DbCommandFilters.AddFilter(new SqlAuditFilter());
```

需要临时绕过：

```csharp
using (DbCommandFilterScope.Suppress<SqlAuditFilter>())
{
    // 此范围不执行该命令过滤器
}

using (DbCommandFilterScope.SuppressAll())
{
    // 此范围不执行任何命令过滤器
}
```

## 2. 核心与插件边界

| 能力 | 归属 | 说明 |
|------|------|------|
| 实体 CRUD、事务、脏数据、雪花 Id | 核心 | 不能插件化，否则主流程不可读 |
| 实体缓存、单对象缓存 | 核心 | CRUD 的读路径依赖它；只保留必要的扩展点 |
| 分片路由、批量写入编排 | 核心 | 由核心决定何时分组、何时批处理 |
| `IEntityFilter` | 插件管道 | 实体层横切逻辑，默认无过滤器时零额外上下文 |
| `IDbCommandFilter` | 插件管道 | 命令层横切逻辑，位于 `DbSession` 中央执行入口 |
| `IDatabase` / `DbFactory` | 提供者插件 | 数据库方言、连接、元数据、批量实现 |
| `IShardPolicy` | 策略插件 | 只负责计算分片，不接管整个 CRUD |
| `IEntityPersistence` | 持久化插件 | 特殊数据库的原生写入适配器 |
| `ICodePlugin` | 工具插件 | 代码生成阶段修正模型 |
| HTTP 服务、备份、ETL | 外围 | 独立服务/工具，不进入核心实体链路 |

### 2.1 为什么缓存和分片不插件化

缓存和分片会改变 CRUD 的语义和一致性边界：

- 缓存决定“什么时候读缓存、什么时候失效”，必须在核心写入链路内闭环。
- 分片决定“一条 SQL 落到哪个库表”，必须在事务和批量编排之前确定。

把这两者做成任意替换的插件，会把主链路拆成难以推理的回调链。保留 `IShardPolicy` 这样的**策略插件**即可，策略只做计算，不接管执行。

### 2.2 数据库提供者插件

`IDatabase` 已经是数据库方言和驱动的边界。内置数据库实现先保留在核心程序集，外部程序集可以通过以下入口注册自己的提供者：

```csharp
DbFactory.Register<MyDatabase>(DatabaseType.MySql);
DbFactory.Register(new MyDatabase());
DbFactory.Register(typeof(MyDatabase));
```

后续可以按需求把内置数据库实现迁到独立包，核心只保留 `IDatabase`、`DbFactory` 和通用 SQL 基础设施。迁移前必须保证现有连接字符串、驱动加载和反向工程行为不变。

## 3. 竞品对照

| 产品 | 横切机制 | 查询过滤 | 数据库扩展 | 对 XCode 的启发 |
|------|----------|----------|------------|------------------|
| EF Core | `SaveChangesInterceptor`、`IMaterializationInterceptor`、`IDbCommandInterceptor` 等多套拦截器 | Global Query Filter | `UseSqlServer`/`UseNpgsql` 等提供者包 | 数据层命令拦截很有价值；但拦截器类型太多，不适合 NewLife 的 20/80 取舍 |
| Hibernate | `Interceptor`/事件系统 | `@FilterDef/@Filter` 命名过滤器 | `Dialect`/驱动 | 事件适合横切，查询过滤要能显式关闭 |
| FreeSql | AOP 字段处理、命令 SQL 改写 | `GlobalFilter.Apply/ApplyIf`，默认作用于 Select/Update/Delete | 数据库包/提供者 | 命名过滤器和命令改写是两个不同层次，不能混在一起 |
| SqlSugar | `Aop.OnExecutingChangeSql` 等 | `QueryFilterProvider`、表过滤器 | `DbType` 提供者 | 命令级 SQL 改写入口简单有效，适合做 `IDbCommandFilter` |
| Dapper | 无内置拦截器 | 主要靠手写 SQL/装饰器 | 驱动 | 核心轻量，但复杂横切逻辑需要额外的边界约定 |

XCode 的选择：

1. **实体层只保留一个 `IEntityFilter` 管道**，不再提供多套 SaveChanges/查询/缓存拦截器。
2. **数据层新增一个 `IDbCommandFilter` 管道**，覆盖 `DbSession` 的所有中心命令执行路径。
3. **数据库提供者通过 `IDatabase` + `DbFactory` 注册**，不把方言写进实体过滤器。
4. **缓存、分片、事务、批量编排留在核心**，只把策略和实现细节放到接口后面。

## 4. 执行顺序与安全

`IDbCommandFilter` 前置按 `Order` 升序，后置逆序，和实体过滤器一致：

```
OnExecuting（Order 升序）
    → 真实 DbCommand
    → OnExecuted（逆序）
```

- `OnExecuting` 可以修改 `context.Sql`/`context.Command`，也可以 `Cancel`/`Handled`。
- `OnExecuted` 可以读取 `Result`、`AffectedRows`、`Exception`，并设置 `ExceptionHandled`。
- 过滤器自身需要执行 SQL 时，必须用 `DbCommandFilterScope.Suppress<TFilter>()` 或 `SuppressAll()`，否则会递归；深度上限为 16。
- 租户/数据权限的原始 SQL 拒绝逻辑仍应留在实体安全过滤器里；`IDbCommandFilter` 不是权限的替代品。

## 5. 分阶段落地

### 已落地

- `IEntityFilter` 单管道，旧 `IEntityInterceptor` 仅兼容。
- `IDbCommandFilter` + `DbCommandContext` + `DbCommandFilterScope`，接入 `DbSession.Execute/ExecuteAsync`。
- `DbFactory.Register(IDatabase)` / `Register(Type)`，为外部提供者预留入口。

### 后续可选

1. 将内置数据库实现按包拆分，核心只保留 `IDatabase`/`DbFactory`/通用基类。
2. 为插件提供统一的启用配置和依赖注入入口，但仍不引入“万能插件接口”。
3. 只在出现真实需求时增加缓存/分片实现插件；默认继续作为核心能力。
